# 任务入口与编排

## 一、请求分类

| 类型 | 示例 | 处理 |
|---|---|---|
| 单项查询 | 查 UAV-001 的电量；教学楼在哪 | 读 data-query |
| 单项计算 | 教学楼东北 20 米的坐标；某区域的搜索框 | 读 spatial-compute |
| 单项航迹 | A 到 B 的航线和距离 | 读 trajectory-generation |
| 动作序列校验 | 检查这段动作序列是否合法 | 读 flight-control，只做 dry-run |
| 感知单项 | 给 UAV-002 开启行人识别；还剩哪些目标没找到 | 读 target-detection |
| 分配咨询 | 我有五架机，搜索教学楼和图书馆怎么分配 | 读 mission-orchestration，只返回分配方案 |
| 飞行任务 | 去教学楼搜索穿红衣服的人；巡逻广场两圈 | 先出确认卡，用户确认后下发 |
| 只规划 | ……只规划不执行 / 先给方案 | 补齐本次方案需要的计算和dry-run|
| 确认卡的回复 | 对上一张待确认方案说确认、修改、取消或追问 | 第三节“用户对确认卡的回复” |
| 运行中指令 | 暂停、继续、全部返航、取消任务、停止跟踪 | 第四节 |
| 中央事件通知 | 待决策、异常、发现目标、任务结束 | 第四节 |
| 状态或原因询问 | 现在进度如何？为什么停了？ | 第四节只读查询 |

## 二、飞行指令校验

**先确认意图和范围，再计算方案。** 下表任一必要信息缺失时，需要用户澄清问题。默认值只限本节末列出的参数，不包括任务目标、区域形状/尺寸、相对方位所需的朝向或执行机身份。

| 条件 | 判断标准 | 不可执行示例 |
|---|---|---|
| 任务意图 | 搜索明确的目标、无目标探索/建图、巡逻、或者单纯飞行 | 只说“搜索某地”时询问找什么，或是否要做无目标探索；不能自行改成探索。|
| 任务地点 | 地名、经纬度或相对位置；只有方向+距离时，按下述“相对基准”区分指定单机与地点库默认位置 | “去附近搜索” |
| 区域 | 只支持圆形和矩形；用户给的形状、尺寸优先，否则使用地点库实际登记的完整区域；两者都没有就询问形状和尺寸 | “起降区附近”只有点位，不能添加圆形或任意半径；“圆形区域搜索”缺半径 |
| 相对方位 | 东西南北等绝对方位可计算；左、右、前、后需要已知朝向 | 缺机头朝向时先询问，不能将“左前方”解释为西北或默认朝北 |
| 参数合理 | 航高在 (0.3, 3.0] m；速度、半径、长宽 > 0；圈数为正整数；经纬度合法 | “速度 -5 m/s”；“航高 10 米” |
| 指令无冲突 | 各项要求不互相矛盾 | “用最大高度 1 米的机，航高 2 米” |
| 完成条件与能力 | 区分任务意图、完成条件、结束动作；工具成功还须能表达用户明确的条件 | 数量去重、全任务总时限、自定义跟踪时长等不能靠格式校验变成已支持 |

- 数值不合理时反问，不取绝对值，也不自行修正。工具中搜索和探索均用几何标签 `task_type="search"`，这个技术标签不改变用户的任务意图。
- “可疑目标”没有明确搜索对象；询问可识别的对象及特征。
- 巡逻按区域边界飞闭合环，只适用于边界可通行的区域；建筑物登记区域的边界会穿墙，巡逻建筑会失败，这时请用户给出建筑外可通行的范围。
- 用户明确要求用固定往返航线扫内部时，边界巡逻和FUEL框内自主探索都不等价；当前未提供固定覆盖航线执行入口，说明缺口，等待用户接受替代后再改变任务表示。
- 只有用户明确说“跟踪”“跟随”时才启用跟踪。
- 用户明确要求载荷（红外、激光雷达等）时才按载荷筛选；普通目视搜索不加载荷条件。

**相对基准**：只有方向+距离且明确指定单架执行机时，语义基准是该机当前位置。状态库坐标只是起飞点记录，不能冒充实时位置；先让用户确认可用该记录作基准，或补充当前位置，再计算偏移。用户已明确指定登记起飞点时直接使用该记录。未指定执行机时用地点库“默认位置”；指定多机但共同参照不明确时询问，不能挑一架代替。

指定速度需核对参与机资源记录的 `max_speed`。超过上限时指出冲突并询问，不自动截到上限；只做咨询时可展示明确标为待接受的限速备选，不能称原速度要求已满足。成本或dry-run成功不证明机型速度限制已核对。

历史复搜需要会话中已有目标特征或可访问的实际历史记录；缺少时询问。离线入口已说明不支持某种历史查询时，不换子命令或遍历不可读目录反复尝试同一能力。

**先核对明确的完成条件**：
- 周期巡逻（每隔一段时间启动一趟、持续若干时段）不同于一次任务内连续巡逻多圈。当前任务入口没有定时启动、间隔等待或跨趟补能调度接口；`laps` 仅表示同一次任务内连续绕行，不能把周期内的总趟数换成圈数，或用搜索时限、重复起降动作代替排程。先说明这一能力缺口，保留用户已给出的单趟圈数、间隔和持续时间，询问是否先给单趟方案；用户接受前不按替代表示继续成本、分配或动作生成。可独立查询地点和机况，但不把单趟dry-run当作周期计划已验证。
- “找目标，找到后仍把整区搜完/建图”是搜索的完成条件，不因“建图”二字就判成两种联合任务。当前 `ALL_TARGETS_FOUND` 按下述规则返航，且覆盖航迹不认证整区覆盖；不能承诺这一条件已实现。说明缺口并保留原要求，不要求用户在已经明确的意图间重新二选一。
- “至少找出N个相同特征的对象”需要物理实体去重计数，不能复制同一描述N次作为N个目标。当前目标清单不保证这项数量条件；按 target-detection 说明边界。不同外观的同类目标仍可分别搜索。
- “必须保证含往返、起降的总时长”与每区 `search_timeout` 不同；当前水平成本与预算不能提供全任务保证。不能把默认速度下的估计超限说成所有允许参数下都物理无解，也不能承诺提高速度后必然满足总时限。
- 用户指定跟踪时长时，先说明当前 profile 固定、不支持自定义；不能把默认 profile 或搜索时限当成该时长。未满足的方案只能明确标作待用户接受的备选，不能称原请求已完整完成。
- 单项航迹与动作校验可以独立使用，但纯飞行/多途经点尚未接入当前完整任务入口和中央作业契约。可以按用户需要提供注明边界的路径预览，不能补搜索动作凑任务，也不能把通用 dry-run 成功称为已可中央下发。

**候选机**：
- 按语义识别机号的角色：明确派遣的机号或候选列表才限定执行机；用作位置参照、查询对象或资源说明的机号不等于执行机。例如“在 UAV-002 左前方探索”中的 UAV-002 只是位置参照。
- 没点名、没说具体架数（“派无人机去搜”），或只是说明资源（“我有五架”）：全部合格机都是候选，由算法决定出动几架，不必追问。
- 要求出动架数（“派两架去搜”）：在数值分配中保留 `constraints.required_drones`，表示恰好这么多架实际作业，不能用待命机凑数。候选不足或约束无解时说明原因，保持数量要求。
- 某作业限定“从这些机中选择”时使用 `constraints.allowed_assignments`；明确某机独占某作业时使用 `fixed_assignments`。允许集合不等于出动数量，不用额外指定数量来代替它。

**默认值**：航高 1.2 m；巡逻 1 圈；搜索时限 1200 s；任务结束后返航并降落（用户明确要求结束后不返航时，改为原地悬停等待指令）；速度不指定时用工具默认值。

无目标探索/巡逻完成后悬停，用中央 `on_search_complete=HOLD` 表达；完整原始动作仍保留工具生成的备用返航/降落段，不能自行删段，见 flight-control。离线交付同时列出策略与备用段，说明不能把整条原始动作直接连续发布。带目标时 `ALL_TARGETS_FOUND` 是另一个待决策条件，不能宣称仅加 HOLD 就改变了它的既有返航规则。

## 三、按需规划与确认

用户要求执行的飞行任务分两轮：第一轮规划并输出确认卡，用户确认后第二轮下发。只规划完成计算后按第五节“只规划”交付，动作使用dry-run返回的本地batch，不套用确认卡的原始WGS84序列。故障补做不出确认卡，直接下发。

根据用户所需结果和已有数据，补齐当前缺少的部分；单项请求在该项完成后即可交付，不要求经过完整链路。

| 当前缺少的内容 | 使用已有技能 | 返回内容 |
|---|---|---|
| 地点、状态、资源事实 | data-query 原SQL查询 | 真实记录 |
| 合格候选机与预算 | data-query 的 prepare_candidates.py | candidates、excluded |
| 明确的数值区域 | spatial-compute 的 resolve_jobs.py；相对位置先用 calc_offset.py | jobs |
| 作业与转场成本 | trajectory-generation 的 planning_routes.py，operation=costs | candidates、jobs、costs、constraints及prepared |
| 无人机归属和访问顺序 | mission-orchestration 的 allocate.py | assignments、owners、unused及求解证据 |
| 分配后的具体航迹和航高 | trajectory-generation 的 planning_routes.py，operation=build | 原始WGS84航点、每机steps、航程估计 |
| 动作序列与格式校验 | flight-control | 每机动作序列、dry-run结果 |
| 目标配置校验 | target-detection | 目标清单及感知dry-run结果 |

成本输入接收候选和数值区域；分配只接收候选预算、作业标识、成本及明确约束。复用成本结果的 `constraints` 保留固定归属和圆形巡逻的单机要求；用户另有逐作业候选集合或数量要求时一并保留，不额外增加用户未要求的出动数量。最终航迹接收同一次 `cost_estimate` 和 `allocation`，不能把归属结果当作航点结果使用。只要已有兼容的数值输入，分配咨询可以直接求解，不必查询地点或生成航迹。

完整只规划方案需按 flight-control 对每架机做dry-run；有目标时按 target-detection 做感知dry-run；报告动作与验证范围。执行请求先出第五节确认卡，用户确认后才进行本节的中央下发操作。只读计算和出卡均不启动感知。

**整理作业**：每个区域一个作业。
- 地名：`{"place":"教学楼"}`。用户指定了形状、尺寸就一并写入，如 `{"place":"教学楼","shape":"circle","radius":5}`。
- 经纬度：`{"name":"…","center_lon":…,"center_lat":…,"shape":"circle","radius":…}` 或 `"shape":"rectangle","length":…,"width":…`。`name` 写用户对该区域的叫法，没有就写“区域1”“区域2”。
- 相对位置：先按第二节“相对基准”确认参照，再用 data-query 查相应记录、用 spatial-compute 的 `calc_offset.py` 算出中心。地点基准有登记区域时用区域中心 `region_center_*`，没有时用该地点的 `longitude/latitude`。相对位置没有登记区域，形状和尺寸要用户给出。
- 用户指定“某机去某区域”时，在该作业里加 `"uav_id"`。
- 地名是否存在由 data-query 查询，区域是否完整由 spatial-compute 的 resolve_jobs.py 校验。仅登记点且用户未给范围时询问形状和尺寸。

**确认卡**：按第五节格式输出，卡片里的动作序列是 flight-control 组装的原始 WGS84 序列。执行模式注册时会再次校验；出卡前不启动感知，也不调用中央。用户在指令里说“直接执行”“不用确认”，也照样出卡，并在卡片前加一句“新任务需要你确认后才会下发。”

**用户对确认卡的回复**（只对最近一张卡有效）：

| 回复 | 处理 |
|---|---|
| 确认（“确认”“执行”“可以”“开始”等，不带修改或疑问） | 进行下述中央下发操作 |
| 修改（改参数、换区域、换机、点名执行机） | 在原指令上只改用户提到的部分，其余沿用；重算受影响的数据并输出新卡，在“注意”里写明差异；旧卡作废 |
| 取消、否定 | 回复“已取消，未下发任何任务” |
| 追问方案 | 按分配结果回答；卡片仍待确认，不下发 |
| 其他新请求 | 旧卡作废，按新请求处理 |

确认时如果上下文里找不到这张卡的编号和动作序列，重新规划并出卡。

**中央下发操作的顺序**（有依赖，不能并行）：
1. `mission_client.py status`：`execution_enabled` 为 true；有目标时 `perception_ready` 为 true；要跟踪时 `target_actions_ready` 为 true；参与机在 `fleet` 里 `available=true`。不满足就停止并报告。
2. 有目标时按 target-detection 为每架参与机准备感知（未运行则 start，已运行则 query），全部机共用同一个 `search_id` 和目标清单；完成后再读一次 `status`，取各机 `fleet.<uav_id>.perception`。
3. 每架机 `register-plan`（可并行；`batch` 逐字复制确认卡中该机的序列，故障补做用已组装结果）→ 一次 `authorize`（`user_intent` 写法见 flight-control）→ `preview` → 立即 `submit`。
4. 任一步失败：不提交；已为本任务新启动的感知，用 target-detection 的停止命令关闭；报告失败的环节和原因，不自动换方案重试。

提交后只回复“已提交”和各机安排，不轮询等待任务完成。

用户看过分配咨询或只规划的结果后要求执行：更新可能变化的状态事实并出卡；之前 dry-run 输出的本地坐标序列不能注册。新方案与之前不同时，在卡片“注意”里写明差异。

## 四、运行中处理

先用 `mission_client.py get` 读最新快照，其中 `revision` 就是下一次控制的 `expected_revision`。命令写法见 flight-control 的 [运行控制](../flight-control/references/runtime-control.md)。

| 情况 | 处理 |
|---|---|
| 目标发现通知 | 用一两句话报告哪架机发现了什么，不需要操作 |
| 决策 `TARGET_ASSIGNMENT_REQUIRED` | 在 `assignment_options` 里选 `eligible=true` 且 `distance_m` 最小的机，`decide assign_target`；没有可选机就报告并保持等待 |
| 决策 `ALL_TARGETS_FOUND` | 搜索完成，全部返航：没有机在跟踪时 `decide return`（scope=mission）；有机在跟踪时，该机 `return` 加 `after_tracking=true`，其余每架机 `return`（scope=uav） |
| 决策 `TRACKING_FINISHED` | 中央已自动恢复该机原搜索：还有目标没找到 → `decide continue`；目标已全部找到 → 该机 `decide return` |
| `exceptions` 里出现 `WAITING_DECISION` | 按下方故障处置 |
| 用户要求暂停、继续、全部返航、取消、停止跟踪 | 分别 `control` pause、resume、return、cancel、stop_tracking |
| 任务结束（SUCCEEDED、PARTIAL、FAILED、CANCELED） | 报告终态、各机作业完成情况、已找到和未找到的目标 |
| 询问进度或原因 | `get`、`events` 只读查询，必要时查执行历史；不重新起飞 |

**故障处置**（某架机出现异常）：
1. 召回故障机：`control return`，scope=uav；该机的异常随之结束。其余机不暂停，继续原计划。返回 ACCEPTED 即可做下一步，召回是否生效看后续事件。
2. 重新 `get` 一次，从最新快照找出故障机未完成的作业（`region_jobs` 中状态不是 SUCCEEDED 的项）和尚未找到的目标。`step_id` 是该机动作序列的步骤号，对照原任务下发时该机的动作序列和作业顺序（确认卡，或补做时的组装结果）得到地点；对不上时不补做，报告未完成的作业。未完成的作业整区重做。
3. 重新查询候选和计算这些未完成作业的成本，再交数值分配：候选查询的 `exclude_uavs` 排除原任务全部参与机（它们仍属于原任务）；成本和航迹的基准航高须高于原任务最高航高至少0.3米，并经航迹工具检查升限，不能在 allocate 中调整高度。
4. 有可行方案：不出确认卡，组装动作后按第三节中央下发操作作为新任务提交：只搜未找到的目标，`search_id` 用新的 `task_key`，`policies` 沿用原任务（`get` 快照里的 `policies`；有 `tracking_target_ids` 时只保留这次要搜的目标）。下发后按第五节报告。没有可行方案：报告这些作业未完成。
5. 召回请求被拒绝时，如实报告阻塞，不另发新请求。

## 五、回复格式

**单项查询或计算**：回答用户所问字段、工具结果及必要限制即可。额外的距离、电量、可行性结论也必须有对应工具结果；没有计算过就不追加。资源硬条件筛选只证明候选条件通过，完整任务可行性还依赖实际区域成本、航迹和当前场景限制。

**信息不足**：指出缺少的必要信息，直接提出澄清问题；不附带基于假设的分配、动作序列或“按你给的范围”等来源说明。

**确认卡**：

```
【待确认】任务方案 T102114235122ad（尚未下发）
任务：搜索“穿红色上衣的人”，发现后只报告，不跟踪
区域：教学楼（地点库登记区域，矩形 12×11 m）；食堂（地点库登记区域，矩形 11.5×9 m）
| 无人机 | 作业顺序 | 航高 | 预计航程 | 预计剩余电量 |
```

- 编号是最终航迹结果的 `task_key`。
- 任务：搜索写“搜索<目标>，发现后只报告，不跟踪”（要求跟踪时写“发现后接近并跟踪”）；探索、建图写“探索（无目标）”；巡逻写“巡逻 N 圈”。
- 区域：每个作业写名称、来源、形状和尺寸，取自区域或最终航迹结果的 `jobs[]`：`area_source=registry` 写“地点库登记区域”，`user` 写“按你给的范围”。相对位置再写明基准点，如“教学楼区域中心东北 20 m”。
- 表格同分配咨询；两架机共用一个区域时，作业顺序写成“中央广场（1/2）”。
- 参数：列出航高、圈数（巡逻）、搜索时限（搜索）、结束后的动作、速度（用户指定时）和出动架数；用户没说的标“默认”，架数没指定时标“由算法决定”，用户给出的值不加标注。

- 没有目标时，“下发时还会检查”只写“无人机在线与占用”。
- 动作序列每架机一行，输出完整 JSON，不省略航点（上例的“…”只为节省篇幅）。

**下发失败**：说明失败的环节和原因、已做的清理（如已关闭本任务新启动的感知），并说明没有任务被提交。

**只规划**：每架机给出（1）ROS 飞控动作序列：dry-run 返回的 `batch`（已转换为该机 MAVROS 本地坐标），JSON 原样输出；（2）规划报告：执行机、作业及顺序、任务类型、航高、预计航程、预计剩余电量、感知配置、dry-run 结果（OK，submitted=false）、未验证项（中央在线预检）。规划失败时只说明失败的环节和原因，不输出动作序列。

**故障通知后**：说明哪架机出了什么异常、已做的处理（召回请求是否被接收）、其余机状态，以及补做结果：已下发时给出新任务的 mission_id 和各机安排（同“执行任务提交后”）；没有可行方案时说明哪些作业未完成。

**分配咨询**：按 mission-orchestration 的回复格式。

## 注意事项

- 地点库的 `longitude/latitude` 是入口，`region_center_*` 是区域中心，两者用途不同；相对位置的基准按第三节“整理作业”选取。
- 航高 `flight_alt` 是任务参数，不是状态库的 `altitude`（记录的当前高度）。
- 多机任务的各机航高由任务航迹工具按基准值间隔0.3米计算。该默认错高不等于用户要求的严格统一航高；无法同时满足时说明冲突。
- 确认卡只用于用户下达的新任务；运行中的控制、待决策处理和故障补做都不出卡。
- dry-run 只证明格式和坐标转换合法；分配只校验给定数值成本和预算，最终航迹报告水平航程及电量估计，未覆盖起降、跟踪和搜索时间上界时明确披露；在线、占用、感知就绪由中央在注册和预览时检查。
- 同一请求重试沿用原 `request_id`，新动作才用新 ID；结果不明时先 `get`/`events` 再决定。
